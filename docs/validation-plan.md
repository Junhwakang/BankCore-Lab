## 4. 실행 테스트 설계

금융 테스트는 실제 PostgreSQL(Testcontainers)을 사용한다. H2나 repository mock으로 락과 제약 동작을 대신 검증하지 않는다. 테스트 실행 환경/DB 버전/데이터 seed를 기록하고 작업 thread마다 독립 연결을 사용한다. sleep만으로 경쟁을 만들지 않고 barrier/latch로 시점을 제어한다.

- 동시 출금: 100,000원 계좌에 서로 다른 키로 10,000원 출금 100건. 인프라 장애 없는 통제 조건에서 정확히 10건 COMPLETED, 나머지는 잔액 부족. 잔액 0, 출금 10건에 해당하는 고객·내부 원장 20행.
- 고객 한도: 두 계좌 충분한 잔액, 당일 4,500,000원 사용 후 500,000원씩 두 동시 이체. 한 건만 성공. 사용액 5,000,000원. 실패 거래는 원장 없음.
- 키 경쟁: 같은 키 100개 요청, 다른 본문 혼합, 다른 고객의 같은 키, 다른 API에 같은 키를 재사용하는 경우 구분.
- 응답 유실: DB 커밋 이후 HTTP 응답만 차단. 재요청은 같은 거래 ID, 성공 원장 2행 유지.
- 종료: 접수 후 종료/실행 중 종료/예약 선점 후 종료. 새 프로세스가 같은 DB로 복구하여 한 거래만 종결.
- 교차이체/동결: A→B/B→A 및 계좌 동결과 동시 실행. 계좌 잠금 뒤 읽은 상태에 따라 한 가지 결과만 확정.
- 예약: 취소/실행 경쟁, 등록/해지 경쟁(수취 계좌 포함), 과거 예약 실행 실패, 인프라 오류 후 복구.
- 마감: 게이트 공유/배타 잠금 경계에 이체를 배치. 전후 각각 한 영업일에만 귀속. 자정 전에 시작해 이후 커밋한 거래도 정의된 기준에 일치.
- 배치: 500건 단위 결과 커밋 전후 종료, 같은 날짜 중복 작업. run/checkpoint/결과 개수 일치 및 재실행 후 원래 스냅샷 보존.
- 손상 탐지: 격리 DB의 별도 테스트 전용 권한으로 잔액을 변경하여 MISMATCHED 확인. 앱 권한의 원장 UPDATE/DELETE는 거절되는지 별도로 확인.
- 부하: 원장 100,000건에서 마감 쓰기 중단 시간, 스냅샷 시간, 대사 시간, 락 대기와 API p95를 분리 측정. 하드웨어/연결 수/동시 사용자/실패율을 함께 공개.

## 5. 설계 검토에서 해결한 모호성

| 발견 내용 | 결정 |
|---|---|
| 내부 정산계정에 고객 잔액 규칙을 적용하면 개념이 섞임 | 원장 자산 계정으로 분리; 비음수 제한은 고객 계좌에 적용 |
| 계좌별 잠금만으로 고객 전체 한도가 보호되지 않음 | 고객 정책 행 잠금 → 계좌 ID 순 잠금 |
| 실패 상태 저장과 금액 롤백 경계가 모호함 | 접수 A/실행 B 분리, 업무 실패와 기술 장애 구분 |
| 실시간 잔액과 어제 원장 비교 시 정상 거래가 불일치 | 마감 게이트 + 영속 스냅샷 |
| 예약 등록·취소·계좌 해지 동시 실행 | 예약 선점 상태, 관련 계좌 잠금, 해지 시 미완료 예약 검사 |
| 잔액이 음수가 아니어도 정수 오버플로 가능 | 잔액/거래 상한·검사 연산·문자열 API |
