# 1단계 기술면접 노트: 요구사항과 금융거래 규칙

이 문서는 최초 1단계 작성 당시의 설명을 보존한다. 2단계에서 보완한 최신 기준은 [요구사항 v1.1](../requirements.md)과 [2단계 면접 노트](phase-02.md)를 따른다. 인수 시나리오는 이후 16개로 확장했다.

## 이번 단계 결과

- 고객, 직원, 관리자의 권한과 시스템 경계를 정의했다.
- 금액, 계좌 상태, 이체 상태, 거래 원장 및 대사의 업무 규칙을 정의했다.
- 구현 이후에도 반드시 유지돼야 하는 7개의 금융 불변식을 만들었다.
- 동시 요청과 장애 상황을 포함한 6개의 인수 시나리오를 만들었다.
- 모듈형 모놀리스 선택을 ADR로 기록했다.

## 1. 왜 구현 전에 금융 불변식을 정의했는가?

### 핵심 답변

일반 서비스의 오류는 특정 화면이나 기능의 실패로 끝날 수 있지만 금융 시스템의 오류는 잔액과 원장 데이터의 불일치로 이어진다. 따라서 구현 방식보다 먼저 어떤 상황에서도 깨지면 안 되는 조건을 정의했다. 이 조건을 동시성 테스트, 장애 주입 테스트, 대사 배치의 합격 기준으로 사용하면 구현의 정확성을 객관적으로 검증할 수 있다.

### 30초 면접 답변

> 금융거래는 API가 200을 반환하는 것보다 데이터 정합성이 유지되는지가 중요하다고 판단했습니다. 그래서 잔액 비음수, 이체의 원자성, 멱등성 키당 단일 결과, 원장 차변·대변 일치 같은 불변식을 먼저 정의했습니다. 이후 구현 선택은 이 불변식을 가장 단순하고 확실하게 지킬 수 있는지를 기준으로 비교하고, 각각을 자동화 테스트로 검증할 계획입니다.

## 2. 다른 접근 방법에는 무엇이 있는가?

### 기능부터 구현한 뒤 테스트 추가

초기 개발은 빠르지만 잘못된 업무 규칙이 코드와 데이터 모델 전체에 퍼질 수 있다. 특히 잔액과 원장 중 무엇이 기준 데이터인지 늦게 결정하면 스키마와 API를 크게 변경해야 한다.

### 화면 중심의 프로토타입

사용자 흐름을 빠르게 확인할 수 있지만 은행 전산직 포트폴리오의 핵심인 트랜잭션, 동시성, 장애 복구 능력을 증명하기 어렵다.

### 처음부터 마이크로서비스로 설계

서비스 분리 경험을 보여줄 수 있지만 분산 트랜잭션이라는 추가 문제가 생긴다. 개인 프로젝트에서는 핵심 금융 규칙을 완성한 후, 실제 측정과 필요성이 있을 때 일부 비핵심 기능을 분리하는 편이 타당하다고 판단했다.

## 3. 실제로 어떤 문제가 발생했고 어떻게 검증했는가?

### 현재 단계에서 발견한 문제

아직 실행 코드가 없으므로 런타임 장애가 발생했다고 주장하지 않는다. 대신 요구사항 검토 과정에서 실제 설계 결함 1건과 다음 모호성을 발견했다.

1. 최초 명세는 입금·출금의 상대 분개가 없어 전체 차변과 대변을 일치시킬 수 없었다.
2. 계좌 테이블의 잔액과 거래 원장 중 무엇을 기준 데이터로 볼 것인가?
3. 같은 멱등성 키에 다른 금액이나 수취 계좌가 들어오면 어떻게 처리할 것인가?
4. 실패하거나 처리 중인 이체를 일일 한도에 포함할 것인가?

### 해결

- 입금·출금의 상대 항목을 기록하는 내부 현금 정산계정을 추가했다.
- 계좌 잔액은 빠른 조회를 위한 현재 값으로 유지하되, 고객 예금계좌의 `대변 합계 - 차변 합계`와 대사할 수 있게 했다.
- 동일 키·동일 본문은 최초 결과를 재사용하고 동일 키·다른 본문은 충돌로 거부한다.
- 일일 한도에는 완료된 출금성 이체만 포함한다.

### 검증 계획

- 각 입금·출금·이체에서 차변 합계와 대변 합계가 같은지 검증한다.
- 계좌 저장 잔액과 `대변 합계 - 차변 합계`를 비교하는 통합 테스트를 작성한다.
- 동일 키에 동일·상이한 본문을 각각 병렬 요청하는 멱등성 테스트를 작성한다.
- 성공·실패 거래가 섞인 상태에서 완료 거래만 집계되는 한도 테스트를 작성한다.

실제 구현 단계에서는 실패한 테스트, 오류 로그, 수정 전후 결과를 별도로 보존하여 이 항목을 실증 자료로 갱신한다.

## 예상 꼬리 질문

### 왜 금액에 `double`을 사용하지 않았나요?

KRW는 현재 프로젝트에서 소수 단위를 다루지 않으며 부동소수점 오차를 제거해야 하므로 원 단위 정수와 데이터베이스 `BIGINT`를 사용한다. 여러 통화나 소수 단위가 필요해지면 통화 코드와 최소 화폐 단위를 함께 모델링하거나 `BigDecimal`을 검토한다.

### 원장을 기준으로 매번 잔액을 계산하면 되지 않나요?

가능하지만 거래가 누적될수록 조회 비용이 증가한다. 현재 잔액을 저장해 빠르게 조회하고, 추가 전용 원장을 감사와 대사의 근거로 사용한다. 두 값의 불일치는 일 마감 대사로 탐지한다.

### 왜 마이크로서비스를 사용하지 않았나요?

현재 규모에서는 단일 데이터베이스 트랜잭션이 금융 원자성을 가장 명확하게 보장한다. 먼저 모듈 경계를 갖춘 모놀리스로 업무와 정합성을 완성하고, 독립 확장이나 장애 격리 필요성이 측정으로 확인될 때 분리하는 것이 합리적이라고 판단했다.

## 본인이 반드시 이해해야 할 항목

- 원자성(atomicity)과 데이터 정합성의 의미
- 멱등성이 단순한 중복 검사와 다른 점
- 저장 잔액과 추가 전용 원장의 역할 차이
- 모듈형 모놀리스와 마이크로서비스의 장단점
- 금융 불변식을 테스트의 합격 기준으로 사용하는 이유
