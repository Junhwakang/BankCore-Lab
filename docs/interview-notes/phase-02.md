# 2단계 기술면접 노트: 데이터 모델과 거래 경계

## 30초 설명

> 계좌·이체·원장·대사를 모듈로 나누되 금융 처리는 하나의 PostgreSQL 트랜잭션으로 설계했습니다. 중복 요청은 고객별 키의 유일성으로 식별하고 거래 행 잠금으로 실행을 직렬화합니다. 고객이 여러 계좌를 써도 일일 한도를 넘지 않도록 고객 정책 행을 먼저 잠급니다. 일 마감에는 같은 경계의 잔액과 원장을 저장하여 재실행해도 비교 기준이 바뀌지 않도록 했습니다. 현재는 설계 단계이고, 다음 구현에서 동시 요청과 장애 주입으로 검증할 계획입니다.

## 직접 설명할 질문

1. 왜 이체 테이블의 상태만 확인하면 부족한가?
   - 두 요청이 동시에 PENDING을 읽을 수 있다. UNIQUE와 행 잠금이 필요하고 금액/원장/종결 상태를 함께 커밋해야 한다.
2. 왜 출금 계좌만 잠그면 안 되는가?
   - 수취 계좌 잔액·동결 상태와 고객 전체 한도도 공유 상태다. 고객 정책 잠금과 계좌 ID 순 잠금을 조합한다.
3. 트랜잭션 롤백 시 FAILED는 어떻게 남기는가?
   - 접수 기록을 별도 커밋한다. 업무 실패는 금액 쓰기 전 확정하고, 기술 장애는 PENDING을 유지하여 다시 실행한다. 불확실한 커밋을 실패로 추측하지 않는다.
4. 왜 잔액과 원장을 모두 저장하는가?
   - 잔액은 즉시 조회, 원장은 변경 근거다. 중복 데이터의 불일치 위험을 한 번의 커밋과 대사로 관리한다.
5. 대사할 때 오늘 잔액을 읽으면 무슨 문제가 생기는가?
   - 어제 마감 이후 이체가 섞인다. 같은 경계의 영속 스냅샷을 비교한다.
6. 일 마감 방식의 한계는 무엇인가?
   - 스냅샷 작성 동안 쓰기 지연과 저장 공간이 든다. 100,000건에서 먼저 측정하고 규모가 커지면 온라인 스냅샷/증분 방식을 비교할 수 있다.
7. 관리자라면 모든 정보를 봐도 되는가?
   - 역할 관리는 금융 조회 권한과 다르다. 역할을 자동 상속하지 않고 직원 조회에도 마스킹과 감사를 적용한다.

## 이번 단계 증거와 다음 단계 증거 구분

이번 단계 증거는 ERD, API 계약, ADR, 요구사항 추적표다. 서버 장애를 해결했다거나 성능이 개선됐다고 쓰지 않는다. 이후 실패한 통합 테스트, 장애 주입 절차, 수정 전후 지표가 생기면 날짜와 커밋을 붙여 실제 경험으로 갱신한다.
