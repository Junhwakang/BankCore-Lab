# BankCore Lab 요구사항 명세 v1.1

상태: 1·2단계 설계 기준선 · 갱신일: 2026-09-14. 구현과 실행 검증은 후속 단계에서 수행한다.

## 1. 프로젝트 목표

BankCore Lab은 가상의 단일 은행 안에서 계좌 개설, 입출금, 계좌이체, 거래 원장 기록 및 일 마감 대사를 수행하는 학습용 금융 시스템이다.

완료의 기준은 기능이 동작하는 것에 그치지 않는다. 동시 요청, 중복 요청, 프로세스 실패가 발생해도 아래 금융 불변식이 깨지지 않음을 자동화 테스트와 측정 결과로 증명해야 한다.

## 2. 사용자와 권한

### 고객(CUSTOMER)

- 본인 계좌와 거래 내역을 조회한다.
- 본인 계좌에서 입금, 출금, 이체, 예약이체를 요청한다.
- 본인의 이체 한도와 처리 결과를 확인한다.

### 은행 직원(OPERATOR)

- 전체 거래의 상태를 검색한다.
- 일 마감 대사 결과와 불일치 항목을 조회한다.
- 실패한 배치의 재실행을 요청한다.
- 고객 비밀번호, 전체 계좌번호 등 민감정보는 조회할 수 없다.

### 시스템 관리자(ADMIN)

- 사용자 역할과 시스템 설정을 관리한다.
- 모든 관리 행위는 감사 로그로 남긴다.

## 3. 범위

### 포함

- 회원가입, 로그인 및 역할 기반 접근 제어
- 원화(KRW) 보통예금 계좌
- 입금, 출금, 동일 은행 내 계좌이체
- 거래 내역 및 현재 잔액 조회
- 요청 멱등성, 동시성 제어, 트랜잭션 처리
- 복식부기 형태의 변경 불가능한 거래 원장
- 예약이체와 일 마감 대사 배치
- 감사 로그, 민감정보 마스킹, 운영 지표

### 제외

- 실제 은행·카드·오픈뱅킹 연결
- 외화, 환율, 대출, 이자 및 수수료 계산
- 실명확인, 공동인증서, 실제 금융 규제 준수 인증
- 네이티브 Android/iOS 애플리케이션
- 프로젝트 초기 단계의 마이크로서비스와 Kubernetes
- 실제 개인정보 및 실제 계좌정보
- 자동 보정 송금 및 보정 거래 운영 API(MVP에서는 불일치 탐지와 조사까지만 수행)

## 4. 용어

- **계좌 잔액(balance)**: 성공한 원장 항목이 반영된 현재 가용 금액. 조회 성능을 위해 계좌 테이블에 보관하되 원장 합계로 검증한다.
- **거래 원장(ledger)**: 금액 변동의 근거가 되는 추가 전용(append-only) 기록이다. 생성된 원장 항목은 수정하거나 삭제하지 않는다.
- **이체(transfer)**: 출금 계좌의 차변과 입금 계좌의 대변을 하나의 논리적 거래로 처리하는 행위다.
- **내부 현금 정산계정(cash clearing account)**: 학습용 입금·출금에서 고객 계좌의 상대 분개를 기록하기 위한 시스템 내부 계정이다. 고객 API에는 노출하지 않는다.
- **멱등성 키(idempotency key)**: 동일 요청이 재전송되어도 결과가 한 번만 반영되도록 고객이 요청마다 제공하는 식별자다.
- **대사(reconciliation)**: 계좌의 저장 잔액과 원장으로 계산한 잔액을 비교하여 불일치를 찾는 작업이다.

## 6. 금융 업무 규칙

### 금액

- 통화는 KRW만 지원한다.
- 금액은 소수점이 없는 1원 단위의 양의 정수로 표현한다.
- 애플리케이션에서는 `long`, 데이터베이스에서는 `BIGINT`를 사용한다.
- 0원 또는 음수 금액의 거래는 거부한다.
- 학습용 기본 한도는 1회 1,000,000원, 1일 5,000,000원이며 설정으로 변경할 수 있다.
- 일일 한도에는 `COMPLETED` 상태가 된 출금성 이체 금액만 포함한다.
- 일일 한도는 **고객별·영업일별**이며 보유한 모든 출금 계좌의 즉시·예약 내부이체를 합산한다. 현금 입출금은 일일 이체 한도에서 제외하되 1회 한도는 모든 금액 변경 요청에 적용한다.
- 기본 한도는 위 값으로 시작하며 관리자 설정은 이후 처리되는 거래부터 적용한다. 처리 중 거래와 설정 변경은 같은 고객 정책 잠금으로 직렬화한다.
- 고객 계좌의 최대 잔액은 1,000,000,000,000원이다. 덧셈 전 상한을 검사하며 Java에서는 오버플로를 검사하는 연산을 사용한다.
- API 금액과 잔액은 숫자로만 구성된 10진 문자열로 주고받는다. 프런트엔드의 정수 정밀도 손실을 방지한다.

### 계좌

- 계좌 상태는 `ACTIVE`, `FROZEN`, `CLOSED` 중 하나다.
- `ACTIVE` 계좌만 입금, 출금 및 이체가 가능하다.
- `FROZEN` 계좌는 조회만 가능하다.
- 잔액이 0원이고 미처리 예약이체가 없을 때만 계좌를 해지할 수 있다.
- 계좌번호는 시스템이 생성하며 전체 값은 고객 본인에게만 표시한다.
- 계좌 개설 잔액은 0원이다. 데모 잔액도 입금 거래와 원장으로만 생성한다.
- 해지 조건의 예약이체는 해당 계좌를 출금 또는 수취 계좌로 참조하는 실행 전·처리 중 예약을 모두 뜻한다.
- 직원은 동결·해제를 수행하고 고객은 본인 계좌를 해지한다. 해지 계좌는 다시 활성화할 수 없다.

### 이체

- 이체 상태는 `PENDING`, `COMPLETED`, `FAILED`로 관리한다.
- 출금, 입금, 거래 상태 변경 및 원장 기록은 하나의 데이터베이스 트랜잭션에서 원자적으로 처리한다.
- 잔액 부족, 한도 초과, 비활성 계좌 및 권한 위반은 금액 변경 없이 실패한다.
- 동일 고객의 동일 멱등성 키와 동일 요청 본문은 최초 처리 결과를 반환한다.
- 동일 멱등성 키에 다른 요청 본문이 들어오면 충돌로 거부한다.
- 이체 수수료는 MVP에서 0원으로 한다.
- 동일 계좌로의 이체는 거부한다. 다른 사람의 수취 계좌는 입력한 계좌번호로 서버가 해석하며 잔액·실명 조회 API를 제공하지 않는다.
- 입금·출금에도 같은 멱등성 규칙을 적용한다. 키는 고객의 모든 금액 변경 API에서 공통 범위이며, 다른 API에 재사용하면 충돌이다.
- `PENDING` 요청 접수는 별도 트랜잭션으로 먼저 저장한다. 업무상 거절은 `FAILED`로 확정하고, DB/프로세스 장애는 `PENDING`을 유지하여 같은 요청을 재처리한다. 실제 금액 변경과 `COMPLETED` 확정은 여전히 하나의 트랜잭션이다.
- 미완료 거래를 다시 조회할 수 있도록 처리 중에는 `202`와 거래 ID를 반환한다. 응답 유실 후 같은 키로 재요청하면 확정 결과 또는 현재 처리 상태를 반환한다.
- 학습용 현금 입금·출금 API는 가상 현금 처리이며 실제 자금 이동을 의미하지 않는다.

### 거래 원장

- 완료된 이체 한 건은 동일 거래 ID를 가진 출금 항목 1건과 입금 항목 1건을 생성한다.
- 내부이체는 출금 고객계좌를 차변, 입금 고객계좌를 대변으로 기록한다.
- 학습용 현금 입금은 내부 현금 정산계정을 차변, 고객계좌를 대변으로 기록한다.
- 학습용 현금 출금은 고객계좌를 차변, 내부 현금 정산계정을 대변으로 기록한다.
- 고객 예금계좌의 원장 잔액은 `대변 합계 - 차변 합계`로 계산한다.
- 내부 현금 정산계정은 고객 예금계좌와 구분된 자산 계정이다. 내부 계정에는 고객 잔액 컬럼을 두지 않으며 자산 잔액은 `차변 합계 - 대변 합계`다.
- 원장 항목은 추가 전용이며 수정과 물리 삭제를 허용하지 않는다.
- 오류 정정은 기존 항목 수정이 아니라 반대 방향의 보정 거래로 기록한다.
- 모든 완료 거래에서 차변 합계와 대변 합계는 일치해야 한다.

### 예약이체와 배치

- 예약이체는 실행 전까지 취소할 수 있다.
- 실행 시점에는 일반 이체와 동일하게 잔액, 계좌 상태 및 한도를 다시 검증한다.
- 실패한 예약이체는 자동 재시도하지 않고 실패 사유를 기록한다. 재시도 정책은 확장 단계에서 결정한다.
- 여기서 실패는 잔액 부족 등 **업무상 확정 실패**다. 처리 중 서버 종료 등 인프라 장애의 `PENDING` 거래는 같은 거래 ID로 복구하며 새로운 송금을 만들지 않는다.
- 예약 등록은 돈이나 한도를 선점하지 않는다. 등록·취소·실행의 경쟁은 예약 행과 계좌 잠금으로 처리한다.
- 모든 시각은 DB에 `TIMESTAMPTZ`, API에 UTC RFC 3339로 표현한다. 예약 시각은 접수 시각보다 미래이고 최대 30일 이내다.
- 일일 한도의 날짜는 `Asia/Seoul` 기준으로 운영하는 **영업일(business_date)**이다. 요청 접수일이 아니라 실행 트랜잭션이 읽은 현재 영업일에 귀속된다.
- 자정 마감 시 금액 변경과 계좌 개설을 잠시 차단하고, 전 계좌 저장 잔액과 원장 합계를 같은 경계에서 스냅샷으로 확정한 뒤 다음 영업일을 연다. 마감 지연 시 실제 경계 시각을 기록한다. 예약 실행도 마감 후 재개한다.
- 자정 이후 영업일이 전환되지 않았으면 신규 금액 실행·계좌 개설은 일시 보류한다. 마감 누락 시 영업일을 순서대로 전환하며 API의 현재 날짜만으로 과거 거래를 재분류하지 않는다.
- 대사는 고정된 마감 스냅샷을 비교하며, 실행 도중 변하는 현재 잔액과 과거 원장을 비교하지 않는다. 불일치는 보고하고 잔액을 자동 수정하지 않는다.
- 대사 배치는 처리 일자와 계좌 ID의 조합으로 중복 결과 생성을 방지한다.
- 배치가 중단되면 마지막 성공 지점 이후부터 재시작할 수 있어야 한다.

## 7. 금융 불변식

아래 조건은 모든 정상·동시·실패 시나리오에서 항상 참이어야 한다.

| ID | 불변식 |
|---|---|
| INV-001 | 어떤 고객 예금계좌도 잔액이 0원 미만이 될 수 없다. |
| INV-002 | 완료된 이체의 출금액과 입금액은 동일하다. |
| INV-003 | 완료되지 않은 이체는 계좌 잔액에 일부만 반영될 수 없다. |
| INV-004 | 동일 고객과 멱등성 키 조합은 최대 하나의 금융 결과만 만든다. |
| INV-005 | 고객계좌의 저장 잔액은 해당 계좌의 `대변 합계 - 차변 합계`와 일치한다. |
| INV-006 | 원장 전체의 차변 합계와 대변 합계는 일치한다. |
| INV-007 | 권한 없는 사용자는 타인의 계좌 원문 정보나 거래를 조회할 수 없다. |

## 8. 비기능 요구사항

### 정합성과 신뢰성

- 모든 금융 불변식은 자동화 테스트로 검증한다.
- 동일한 요청을 재시도해도 결과가 달라지지 않아야 한다.
- 배치 재실행은 이미 완료된 결과를 중복 생성하지 않아야 한다.

### 성능

- 동일 계좌에 대한 동시 출금 요청 100건에서도 음수 잔액과 중복 원장이 없어야 한다.
- 정의된 로컬 테스트 환경에서 100,000건의 원장을 대상으로 대사 시간을 측정하고 결과를 README에 기록한다.
- API 성능 수치는 실행 환경, 데이터 크기, 동시 사용자 수와 함께 공개한다.

### 보안

- 비밀번호는 단방향 해시로 저장하고 평문을 저장하거나 로그에 기록하지 않는다.
- 계좌번호, 사용자 식별정보 및 인증 토큰은 로그에서 마스킹한다.
- 모든 API는 최소 권한 원칙에 따라 접근을 제한한다.
- 비밀값은 소스코드나 Git 저장소에 커밋하지 않는다.

### 관측 가능성

- 각 요청에는 추적 가능한 상관관계 ID를 부여한다.
- 거래 성공·실패, 처리시간, 데이터베이스 오류 및 배치 결과를 구조화 로그와 지표로 남긴다.

## 9. 핵심 인수 시나리오

### AC-001 정상 이체

- Given 출금 계좌 잔액이 100,000원이고 두 계좌가 활성 상태일 때
- When 고객이 30,000원 이체를 요청하면
- Then 출금 계좌는 70,000원, 입금 계좌는 30,000원 증가하고 이체와 원장 두 항목이 완료 상태로 기록된다.

### AC-002 잔액 부족

- Given 출금 계좌 잔액이 10,000원일 때
- When 고객이 20,000원 이체를 요청하면
- Then 거래는 실패하고 양쪽 계좌 잔액과 원장은 변경되지 않는다.

### AC-003 중복 요청

- Given 동일한 멱등성 키와 요청 본문이 있을 때
- When 같은 요청을 여러 번 전송하면
- Then 최초 결과만 한 번 반영되고 모든 응답은 같은 거래를 가리킨다.

### AC-004 동시 출금

- Given 출금 계좌 잔액이 100,000원일 때
- When 10,000원 출금 요청 100건을 동시에 전송하면
- Then 인프라 장애가 없는 조건에서 정확히 10건만 성공하고 나머지는 잔액 부족으로 실패하며 최종 잔액은 0원이다. 원장과 잔액이 일치한다.

### AC-005 처리 중 실패

- Given 이체 처리 도중 의도적인 예외가 발생할 때
- When 트랜잭션이 종료되면
- Then 출금과 입금 어느 쪽에도 부분 반영이 없어야 한다.

### AC-006 일 마감 대사

- Given 계좌 저장 잔액과 원장 합계가 일치하거나 의도적으로 불일치할 때
- When 대사 배치를 실행하면
- Then 각 계좌는 `MATCHED` 또는 `MISMATCHED`로 분류되고 차액과 실행 이력이 저장된다.

### 추가 인수 시나리오

| ID | 상황과 합격 기준 |
|---|---|
| AC-007 | 같은 고객·키에 다른 금액/API/수취 계좌 → `409 IDEMPOTENCY_CONFLICT`, 추가 원장 없음 |
| AC-008 | 같은 고객의 두 계좌에서 병렬 이체 → 완료 합계가 고객별 당일 한도를 넘지 않음 |
| AC-009 | DB 커밋 후 응답 유실 → 동일 키 재요청이 동일 거래 ID와 결과 반환, 금액 한 번 반영 |
| AC-010 | 접수 후·실행 중 프로세스 종료 → 남은 `PENDING`을 재실행해 부분 반영 없이 하나의 결과 확정 |
| AC-011 | 예약 취소와 실행 경쟁 → 취소 성공이면 송금 없음, 실행 선점이면 취소 `409`, 송금 최대 한 번 |
| AC-012 | 마감 전후 이체와 대사 재시작 → 이체는 한 영업일에만 귀속, 확정 스냅샷 재사용, 결과 중복 없음 |
| AC-013 | 타인 계좌 ID 조회/출금, 직원 원문 조회 → 접근 거절 또는 마스킹, 민감정보 로그 없음 |
| AC-014 | 잔액 상한 초과·금액 오버플로 → 금액과 원장 변경 없이 거절 |
| AC-015 | 입금·출금 각각 고객/내부 상대 분개 2건, 차변=대변, 고객 잔액=대변−차변 |
| AC-016 | 계좌 해지와 예약 등록 경쟁 → 해지 계좌를 참조하는 유효 예약을 새로 만들 수 없음 |

## 10. 1단계 완료 기준

- 사용자와 시스템 경계가 정의되어 있다.
- 핵심 기능과 제외 범위가 구분되어 있다.
- 금액, 계좌, 이체, 원장 및 배치 규칙이 정의되어 있다.
- 검증 가능한 금융 불변식과 인수 시나리오가 존재한다.
- 주요 아키텍처 선택이 ADR로 기록되어 있다.

이 문서는 구현 과정에서 변경할 수 있으나, 변경 시 이유와 영향을 ADR 또는 변경 이력으로 남긴다.
